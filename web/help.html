One tick, start to finish

A program is an ordered list of WHEN … THEN … rules. You never steer a robot; you decide, once, what it should do in every situation it can recognise. Every tick the robot starts again at rule 1 and walks down:

  1. Test the rule's condition against what the robot perceives right now. Nothing is remembered between ticks except the three memory points.
  2. If it does not match, move to the next rule.
  3. If it matches, run its actions. A primary action — move, turn, navigate, pick up, deposit, drop, attack — is the robot's move for this tick and ends the tick: no rule below it is even looked at.
  4. A rule holding only side effects — the five memory writes and the two broadcasts — costs no time. It runs and the walk continues down the list.
  5. If no rule matches at all, the robot idles for the tick. That is safe, but it is also a robot doing nothing — with one exception, below.

This is the one rule of the language you have to hold in your head. A rule that only remembers something is not a decision — it is a note taken on the way past, and a lower rule still gets to act on the same tick.

The one thing you never have to program

A robot standing at its own base holding a component puts it in the base. No rule needed. You can write one — and if you do, it runs — but you do not have to, and the template does not. It is part of running your program, so a recalled robot — whose program is suspended while it walks home — holds its cargo until you install a program on it, and only then is anything, reflex included, deciding its ticks again.

It is the only reflex in the language, and it is there because it is not a decision: a component you are carrying is worth nothing to your score, you can only carry one at a time, and your base is the only thing that will take it. There is no program that wants to stand on its own base holding a component it refuses to put down.

It never overrules you. The reflex only takes a tick the program was going to waste anyway — nothing matched, or the rule that matched had nothing to aim at, or it said go home while already home. Anything you actually chose wins: a turn, an attack, drop_component, even stop. If you want the component left on the ground at your own base rather than scored, say so with drop_component and that is what happens. In the match inspector these ticks read at own base carrying a component: depositing is automatic, so you can always see when it was the reflex and not one of your rules.

Rule order is the program

Below is one tick of a scavenger that is carrying a component and can see another one. Read it top to bottom, the way the robot does.

1 WHEN sees_component AND carrying_component THEN save_visible_target(1) matched · side effect · keeps going Point 1 now holds where that component was. Zero ticks spent, so the walk continues.
2 WHEN carrying_component AND sees_enemy_robot THEN move_away_from_target no match Nothing hostile in the wedge, so this rule is skipped — but it is above rule 3 for a reason.
3 WHEN carrying_component THEN move_to_own_base matched · primary · ends the tick One step along the route home. The tick is over here.
4 WHEN component_in_reach AND carrying_nothing THEN pick_up_component never reached
5 WHEN sees_obstacle THEN turn_random never reached

Three things follow, and every one of them has bitten somebody:

  • Swap rules 2 and 3 and the robot walks home through the enemy. Rule 3 matches whenever rule 2 does, so the more specific rule has to sit above it. A rule that a higher rule always covers is dead code, and the editor marks it unreachable_rule.
  • Nothing is a subroutine. Rule 3 does not "walk home"; it takes one step home. Next tick the whole list runs again, and if an enemy appears, a higher combat rule pre-empts the walk mid-journey. That is the intended way to write reactions.
  • A specific rule goes above a general one. Put the general fallback (carrying_nothing THEN move_forward) last, or it eats every tick.

Combining conditions: ALL, ANY and NOT

A condition is one dropdown, or a box holding several. The editor gives you three kinds of box, and the box is the grouping — there is no operator precedence to remember, because there is nothing written on one line to be ambiguous about.

  • ALL of — every condition in the box must hold.
  • ANY of — at least one must hold.
  • NOT — holds exactly one condition, and is true precisely when that condition is false. Press NOT on a condition to wrap it, or on a group's header to invert the whole group.

Which condition a NOT covers is the thing to get right, and the boxes make it visible. These two are different programs:

A NOT ( sees_enemy_robot AND weapon_ready ) One NOT box, an ALL box inside it. True unless both hold — so it is true with an enemy in sight and the weapon still reloading.
B ( NOT sees_enemy_robot ) AND weapon_ready One ALL box, a NOT box inside it. True only with no enemy in sight and the weapon loaded — the opposite answer in exactly the case above.

Two things NOT changes about the warnings, both worth knowing before you reach for it:

  • A negated condition is often already true at spawn. A fresh robot sees nothing, hears nothing and detects nothing, so NOT sees_enemy_robot holds on tick one. That is usually what you wanted — it is also why a rule that only negates world conditions fires immediately and can eat every tick if you leave it near the top.
  • Negating a condition your robot cannot sense is a trap. On a blueprint with no radar, radar_detects_target is permanently false, so NOT radar_detects_target can never fail and that part of the rule tests nothing. The editor says so with always_true_predicate — the negated twin of dead_predicate. What the rule then does depends on where you put the NOT: inside an ALL box the other conditions still decide, but a NOT wrapped around the whole box makes the rule fire every tick.

One thing the editor deliberately will not tell you: whether a rule holding a NOT is made unreachable by a rule above it. Working that out in general is the same problem as deciding satisfiability, so unreachable_rule stays quiet on any condition containing a NOT (and on any containing an ANY, for the same reason) rather than guessing and marking a live rule dead. Use Dry run: a rule that never fires in a few hundred ticks shows up on its own card.

What a robot can actually perceive

A robot has no map. It knows where it stands, where its own base is, what it carries, what is in its three memory points — and whatever its sensors report this tick. Sensors are the part that surprises people.

Forward vision is a wedge, not a circle

The robot below stands in the middle facing right. It sees a 90° wedge in front of it, out to 6 cells — and nothing at all behind or beside it. Turning is how you scan.

the robot sees_component — in the vision wedge component_in_reach — close enough to pick up

The pair that catches everybody: sees_component is true for anything in that whole wedge, six cells away included — and pick_up_component will do nothing from there. component_in_reach is the eight cells around the robot plus its own cell, and it does not care which way the robot faces: the orange cells behind it count. The scavenger loop is see → navigate → reach → pick up, and skipping the middle step is the most common broken program.

Radar sees everywhere, and much further

Same robot, same heading, now with a parts radar installed, drawn at half scale. Radar reach is 16 cells in every direction; the enemy-base radar reaches 28. A blueprint may carry one radar, and each kind reports exactly one class of thing — loose components, enemy robots, or enemy bases.

the robot radar_detects_target also inside the vision wedge

That difference in area is the whole argument for spending mass on a radar. Without one, a robot finds things only by turning until they wander into the wedge.

The conditions that look alike

This oneNot this oneThe difference
sees_component component_in_reach The green wedge ahead versus the orange ring around. Seen is not grabbable; in reach ignores facing.
point_is_set at_point "I remember a place" versus "I am standing on it". A program that tests only at_point waits for a coincidence; one that tests only point_is_set never notices it has arrived and orbits forever. Real navigation uses both, arrival rule first.
visible target radar target Two different target lists. move_to_visible_target and attack_visible_target use the wedge; move_to_radar_target and attack_radar_target use the radar contacts, which may be far behind the robot. Both idle harmlessly when their list is empty — and an idle tick looks exactly like a bug.
sees_enemy_robot visible_target_in_weapon_range Seeing something is not the same as being able to hit it. Each weapon has its own reach: the short ones stop well inside the vision wedge, and the long ones outrange it, which is what attack_radar_target is for. Test the range condition, not just the sighting, or the robot fires at nothing.

Turning: eight headings, one step at a time

turn_left and turn_right move the robot's facing by one of the eight compass points — 45°. Looking behind you is four turns, not two, and each one costs ticks. This is why a search program that turns on every obstacle covers ground so slowly, and why a heavy chassis is bad at searching: turning is priced off the same speed the chassis moves at.

Memory and signals

  • Every robot has three memory points, numbered 1 to 3. Each holds one coordinate, or nothing.
  • They start empty, and they are wiped whenever you install a program on the robot at its base. A program cannot assume a point is set — some rule of its own has to set it.
  • Writing a point replaces what was there. Memory is private to one robot and dies with it.
  • Signals are not memory. received_come_here is true for one tick only. If the same rule does not save_signal_position, the position is gone for good.

The three worked programs, and the badges they earn

The editor's Start from a template… menu loads the three programs from the design document, as printed — except that the scavenger no longer carries the deposit rule the document opens it with, since that is the reflex above. All three are worth reading, and none of them is clean — which is the useful part, because the editor tells you why.

TemplateWhat the editor saysWhat it means
component scavenger (§10.7) missing_component error and dead_predicate warning — on a blueprint with no radar Its search step is move_to_radar_target. Fit a parts radar and the program is a working scavenger; leave it off and it is a blind random walk that only ever finds what stumbles into its wedge. Pick the scavenger blueprint and both markers disappear.
memory-assisted scout (§10.8) inert_start warning A fresh robot has empty hands and empty memory, and every rule needs one or the other. Nothing in the world can start it, so it stands at its base forever. Add one fallback rule at the bottom — carrying_nothing THEN move_forward — and it comes alive. This is the warning to take seriously.
defensive responder (§10.9) reactive_start note Not a fault. It also does nothing at the start, but what it waits for — seeing an enemy, hearing a signal, a radar contact — can arrive from outside. A guard that stands still until something happens is a legitimate design, so this one is grey, not coloured.

Three more markers you will meet: forward_only (the robot can drive but never turn, so the first wall stops it forever), unreachable_rule (a rule above always matches first) and always_true_predicate (a NOT over a condition the blueprint cannot sense, so the negation tests nothing). Errors block saving; warnings and notes never do.

Write your first scavenger

Five rules, in this order. Every one of them is a dropdown in the editor. There is no deposit rule: arriving home with a component puts it in the base on its own.

  1. WHEN carrying_component THEN move_to_own_base — one step per tick, re-decided every tick.
  2. WHEN component_in_reach AND carrying_nothing THEN pick_up_component — the orange ring, not the green wedge.
  3. WHEN sees_component AND carrying_nothing THEN move_to_visible_target — close the gap between seeing and reaching. With a parts radar, put radar_detects_target THEN move_to_radar_target above this and the robot stops depending on luck.
  4. WHEN sees_obstacle THEN turn_random — without a turn somewhere, the robot jams against the first wall.
  5. WHEN carrying_nothing THEN move_forward — the fallback that keeps it moving, and the reason it is never inert.

Then press Dry run: it runs the program in a practice arena and reports which rules actually fired. A rule that never fires in a few hundred ticks is either unreachable or waiting for something that never happens.
